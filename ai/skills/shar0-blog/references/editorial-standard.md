# shar0.dev 文章標準

依 2026-09-05 到 09-06 跟作者的訪談 (Q1 到 Q46) 整理，訪談紀錄不在 repo 裡。這份是寫作、重寫與交付前檢查的判準。實際跑過文章後冒出的新規則，補在對應章節。

## 1. 目的與讀者

每篇文章圍繞一個核心問題，讓讀者看懂答案怎麼推導出來，並能在相似情境判斷什麼時候適用。

讀者是會寫 code 但不熟這個主題的工程師，也包含日後回來複習的作者。讀者看得懂基本 code、常用術語，能做合理推論。主線需要的新概念用精簡說明或具體例子接上，離主線遠的給連結。不為了涵蓋所有程度逐一展開讀者自己推得出來的細節。

AI 味不是作者身分的判定，是編輯問題的線索: 缺主線、重複解釋、宣傳句、刻意熱鬧的用字、過度展開。處理方式都在後面的章節。

## 2. 語氣

工程師向同事說明自己弄懂的事情。直接、平實、可以口語。

- 口語靠選詞，不靠語氣詞。頂多、很難搞、其實、基本上、就是、根本、卡住、搞、弄，放行。句尾的呢、吧、喔、啦、嘛、耶不用
- 程度停在跟同事講解，不到聊天。幹嘛、爛這類聊天用語不進文章
- 人稱: 「我」只用在自己的判斷、經驗與取捨。不用「我們」帶讀者走 (讓我們來看看)。對讀者說條件時用「你」。不用「您」
- 反問句可以用，但不開場、不連用。帶著真問題的可以 (這個地方需要鎖，是為了避免重複工作，還是避免資料出錯?)，開場白式的不行 (你有沒有想過…)
- 比喻的判準: 拿掉比喻，靠 code 例子讀者是否已能理解。能就刪。一個概念一個比喻，不換一個比喻重講一次
- 技術結論的語氣要配得上證據與適用範圍

語氣基準見 voice-samples.md。

## 3. 用字

### 技術名詞

預設英文。下面清單指定中文的用中文。

| 用中文 | 記憶體、型別、預設、支援、品質、陣列、字串、迴圈、變數、回傳、效能、網路、資訊、檔案、使用者、相容、連結、資料 |
| --- | --- |
| 用英文 | cluster、code、function、class、interface、object、thread、server、cache、queue、call |
| 皆可，一篇內固定一種 | 執行緒 / thread、物件 / object、快取 / cache、佇列 / queue、呼叫 / call |

清單外的詞走英文。不用中國用語: 數據、配置、集群、代碼、內存、線程、對象、函數、類、類型 (指型別時)、默認、服務器、支持、質量、接口、緩存、隊列、數組、字符串、循環、變量、調用、返回、性能、網絡、信息、文件 (指檔案時)、用戶、兼容、鏈接。

### 英文詞的寫法

- 一般名詞小寫: server、client、thread、class、worker、lock
- 專有名詞照官方: Redis、Redlock、JVM、Kubernetes、Rust Book
- 不加複數 s: 兩個 worker，不是兩個 workers
- 不括號附中文。fencing token 就是 fencing token。用中文的詞也不括號附英文: 寫多型，不寫多型(Polymorphism)。例外: 這個詞後面會以另一種形式出現 (標題中文、code 裡是英文識別字)，第一次括號一次，之後固定一種
- 程式識別字用反引號: `play()`、`Instrument`、`Arc<Mutex<T>>`。一般名詞不用反引號: class 當名詞就寫 class，`class` 當關鍵字才用反引號
- 中英之間加空格

### 空轉詞

看到先做刪除測試: 拿掉後資訊、語意與語氣沒有必要的損失，就刪。會改變技術含義的限定詞保留。這張清單是起點不是禁用表，口語詞一律放行。

- 評價詞: 強大、不可或缺、極具價值、經典、魅力、秘密、優雅、輕鬆、無痛、又快又省力、瞬間暴增
- 程度副詞: 十分、極其、相當、顯著、大幅、真正、完全 (非常是作者口語，放行)
- 空轉連接: 值得注意的是、換句話說、簡而言之、總的來說、首先／其次／最後、接下來我們來看、綜上所述、不難發現、可以說
- 書面動詞: 揭示、探討、闡述、進行、實現、具備、達到、提供了。改成講、說、看、做，或直接刪
- 標題詞: 深入、完整、指南、攻略、一次搞懂、全解析、必知
- 擬人與戲劇: 趁機、終於醒來、魔法、大小姐、炸彈客

### 粗體、斜體、emoji

- 粗體只標讀者掃過去要抓的那個條件或那句判斷，一節最多一兩處。術語第一次出現不粗體，動詞不粗體
- 不用斜體
- 不用 emoji

## 4. 標點與數字

照作者打字習慣，不照排版規範。

- 逗號、句號、問號、頓號全形
- 冒號、括號半形。冒號後空一格: `簡化問題: 找到`
- 引號盡量不用，改寫成不需要引號的句子。真要引別人的話用半形雙引號。字元與字串字面值用反引號
- 不用破折號、省略號、驚嘆號。破折號改逗號或拆句
- 句號只用在段落中間句子之間。段尾、列點、小標題、表格格內不加
- 數字預設阿拉伯數字加空格: 2 個 worker、8 bytes、version 從 1 改為 2。口語小量 (兩個、三種) 不強制改
- 分號不用，依意思拆句

## 5. 句法

從作者句子反推的規則，不是通用中文寫作規範。

1. 子句短可以串逗號，子句長就拆。一句一個動作或一個判斷
2. 「的」一句最多兩個。多了改語序或拆句
3. 動詞直接用。進行部署 → 部署，對 X 進行比較 → 比較 X，透過 X 來 Y → 用 X 做 Y
4. 主動句。被設計來用作 → 用來。被動只在受事者才是重點時用
5. 條件在前，結論在後
6. 關聯詞刪掉直接並列。不僅…也、無論…都、既…又，拿掉多半還成立。三個一組的排比留一個有資訊的
7. 「是…的」判斷句直接說。是不安全的 → 不安全

範例: 「揭示了為什麼依賴超時自動釋放的鎖在正確性場景下是不安全的」→「鎖靠 TTL 自動釋放，遇到要求正確的場景就不安全」

## 6. 段落與節

- 段首句先一句情況再判斷: 讀者剛看到什麼、會想什麼，然後才是這段的判斷或要看的東西，後面接理由和例子。像在跟同事講話，不是先丟定義或 code。讀者只讀每段第一句也能跟上主線。解題文的推導段例外，那裡是案例 → 觀察
- 段落之間不寫過渡句。接下來我們來看、說完 X 再看 Y、在深入之前，全刪。上一段結尾不預告下一段
- 節的第一句不重複小標題，也不用規則定義或 code 開場。先承接上一節讀者會冒出的疑問或情況 (上面那兩行看起來有點多此一舉…、第一次踩到會覺得跟前面講的矛盾)，再進判斷或 code
- 節結尾不小結，講完就換節
- 一個概念一個解釋。一個比喻夠就不加第二個，一個例子夠就不加第二個
- 段落長度依一個意思是否講完決定，不硬切

### 段落與列點

正文以連貫段落為預設，解釋與推導由段落承載。列點、表格、編號只在有助閱讀時用: 故障時間線、操作順序、真正需要並列比較的內容。內容可以並列不代表一定要拆成清單，拆多了像技術文件不像文章。列點項目短，一行內講完，超過一行就該是段落。原始筆記的 bullet 不原樣搬進文章。

### 小標題

短、具體、保留技術詞，讓讀者定位內容。核心觀念、深入探討這類不增加辨識資訊的字眼刪掉。例: 鎖失效的代價、鎖過期後的寫入、Fencing token 與儲存端檢查、Redlock 的時間假設。解題文的 Solution、複雜度、限制夠具體，保留。思考、Coding 流程、第一步不具體，改寫成那節的觀察。

### 層級

- H2 是節。H3 只在一節裡有真正並列的子項時用。不用 H4
- 內容只有一兩行的不成節，改成一張表或一段
- 一節的小標題超過 6 到 7 個，先檢查是不是兩篇文章擠在一起

### 拆文信號

不看字數。出現以下情況就拆:

- 開頭寫不出一句判斷，或那句判斷有兩個「而且」
- 小標題能明顯分成兩群，各自服務不同的問題

系列文拆成 7-1、7-2，原本的 7-2 順延。slug 不動。

## 7. 程式碼、連結、圖、引用

### 程式碼

- 程式碼前一句說要看什麼: 把 `Wind` 放進 `Instrument` 變數再 call `play()`。程式碼後一句說結果和為什麼。前後不重複
- 主範例最小可執行，預期輸出寫在註解裡: `// 印出 Wind.play()`
- 區塊帶語言標記
- 後續變化只貼改動的幾行，前後用 `// ...` 表示省略
- 一個範例家族貫穿全文，第二個家族只在展示主範例做不到的差異時才引入
- 範例不綁書。可以換成中文讀者更熟的情境，但時事範例要能不靠當時背景也看得懂

### 連結

- 掛在句子裡的名詞上: [Martin Kleppmann 的原文](url)、6-3 講過[向上轉型](url)。不寫 (請見連結)、更多資訊請參考、詳見
- 一個來源掛一次，同一段不重複掛
- 系列內互連一樣掛在概念名詞上，不寫上一篇，讀者不一定按順序讀

### 圖

- 文字說不清的結構才畫，時序用編號列點就夠
- 寫作時不畫圖，在該放圖的位置留 `[圖: 鏈接環的結構，標出雙人環例外]` 加一段 mermaid 草稿，作者決定要不要畫

### 引用

- 預設轉述，用自己的話講原作者的主張，連結掛在主張旁
- 原句措辭本身是重點時才引，保留英文原句不翻譯，半形雙引號，後面用中文接著講
- 一篇不超過兩三句

## 8. 標題、摘要、開頭、收尾

### 標題

格式: 系列識別 + 編號 + 核心問題或差異。後半段必須能從「本文解決什麼問題」那一句壓縮出來。

| 類型 | 格式 | 例 |
| --- | --- | --- |
| SD 閱讀筆記 | 【SD閱讀筆記】編號 - 原作者 談 核心議題 | 【SD閱讀筆記】02 - Martin Kleppmann 談分散式鎖: Redlock 真的安全嗎? |
| 概念講解 (系列) | 【系列名】章-節 核心問題或差異 | 【Thinking in Java】7-1 宣告成父型別，為什麼執行的是子類別的方法? |
| 概念講解 (非系列) | [語言] 核心問題或差異 | [Rust] Box 還是 Arc: 單一所有者，還是跨執行緒共用? |
| 解題推導 | 題號. 英文題名 | 2127. Maximum Employees to Be Invited to a Meeting |

問句和主題式都可以。系列識別不寫「筆記」(書名已交代來源)。編號不加括號。改標題不改 slug。

### 摘要 (Ghost 的 excerpt 欄位)

一兩句，寫核心問題與判斷。填在 Ghost 的 excerpt，不放進正文，正文第一段直接進問題。不描述文章手法 (透過生動比喻…)，不寫幫助初學者快速上手。

### 開頭

一般文章前一兩段交代核心問題與簡短判斷，正文再說明怎麼得到。第一句用一句話講讀者會在什麼情況碰到這個問題，像在跟同事講話 (向上轉型講完之後馬上會碰到一個問題…)，接著才是問題、行為和答案。只給答案不給問題，讀者不知道為什麼要讀這篇。不用 code 片段或考題當第一句，那讀起來生硬。解題文先點出卡關處與關鍵觀察。不用反問開場白 (你有沒有想過…)，不寫背景句 (在現代軟體開發中…)，不預告 (接下來揭開它的秘密)。

### 收尾

講完即結束。需要時一段留下可帶走的判斷或仍未解的問題。不加總結章節，不逐節重列，不寫建議動手練習、親身體會威力這類話。

## 9. 三類骨架

共用上面所有規則，各自的章節設計不同。這些是路徑不是表格，不為填滿而加內容。

### 9.1 SD 閱讀筆記

目的: 把原文精華濃縮，簡單傳遞給讀者。原文的核心論證形成可以連續閱讀的主線。

1. 標題: 系列識別、原作者、核心議題
2. 開頭: 短段落交代原文完整標題、連結與核心判斷
3. 原文精華: 按必要核心論點分節，每節保留關鍵理由與足夠理解的例子，以連貫段落推進。會影響核心結論的不同論證都保留，不因為都涉及同一主題就合併。重複舉例、歷史背景、旁支細節省略
4. 評析與收尾: 有具體判斷才加評析，不為湊心得添加。短評只針對眼前一個論點時放在相關段落後，交代歸屬。要串多個論點才能討論的另成一節。最後一個論點講完就可以結束

為了忠實講清原文而補的必要解釋屬於原文整理本身。原作者觀點、筆記中的情境推演、個人經驗與未解問題要分清歸屬，不確定就用中性表述或問。

### 9.2 概念講解

目的: 讀者能解釋眼前行為，也能推測條件稍改後的結果。Thinking in Java 系列定位為新手向，傳遞當篇核心觀念。這不表示所有概念文都只能入門深度。

1. 標題: 系列識別 + 編號 + 核心問題
2. 摘要: 一兩句核心問題與判斷
3. 開頭: 第一句講讀者會在什麼情況碰到這個問題，問出問題，貼最小例子，給答案。系列的前置知識用一兩句接上、連結到前一篇，不重講
4. 正文: 沿例子推進，先看到行為再解釋原因，需要時才引入術語。主範例可執行、附預期輸出，後續變化只貼修改處。一個範例家族貫穿全文
5. 深度: 底層實作只在核心問題用得上時展開
6. 邊界: 例外與容易誤用的情況，判準是這個例外能不能反過來把核心機制的邊界說得更清楚。能就留，並明講那條邊界。不能就刪或降級成一句帶連結的提醒。單一例外就近寫在相關概念後，多個例外共同劃出同一條邊界時合併成節，小標題寫那條邊界，不固定叫常見陷阱
7. 收尾: 講完即結束，需要時一段可帶走的判斷

系列維持照書的小節切，每篇要能用一句話說出核心問題，說不出來就拆。方案比較 (Box vs. Arc) 也走這個骨架，核心問題就是什麼情況該選哪個。

### 9.3 解題推導

1. 標題: 題號. 英文題名，不加副標
2. 題目: 連結、用自己的話一兩句講題意，不整段翻譯。限制只列會影響解法的
3. 卡關與關鍵觀察: 題目講完就一兩句，這題卡在哪、關鍵觀察是什麼。正文再展開為什麼
4. 推導: 小案例 → 認出結構 → 觀察 → 演算法。小案例只列能暴露結構的那幾個，不窮舉 edge。這裡的段落是案例 → 觀察，是段首句規則的例外。⇒ 箭頭式推導只在這類文用
5. 實作: 關鍵片段分段貼，最後完整 Solution
6. 複雜度: 時間、空間各一行，不推導。推導本身就是關鍵觀察時例外
7. 其他解法: 只在改變判斷時寫。從兩次掃描收成一次值得，換語言重寫不值得
8. 收尾: 可以沒有。這題的觀察能推廣時一句帶走

## 10. 補充與來源

只補會影響核心判斷的資訊，延伸知識附來源讓讀者自己追。

- 關鍵推導跳步、有爭議的主張、影響結論的具體數字，補必要說明與來源
- 優先連原始文章、官方文件或 code
- 來源足以支持本文範圍內的結論就停，不沿每條來源往外展開背景知識
- 找不到依據時縮小、刪除或簡短標記，不用加長文章掩蓋證據缺口
- 限制條件只寫會改變結論或選擇的
- 可新增教學用假設例子，交代是假設。執行過才稱已驗證
- 作者的經歷、實測、個人取捨不補造。涉及核心內容且資料不足時問作者
- 涉及目前版本能力時用目前資料，討論歷史文章觀點時標清時點

## 11. 取材與待研究題目

原始筆記有用的內容不必全數收入。取材以核心問題為準，重複的選型表、小抄、總結可以合併。

能獨立成篇但需要後續研究的支線，收進待研究題目，放在正文外的區塊，作者自己收。當次只留研究入口，不展開、不開始追查。每題記:

- 暫定題目與切入問題
- 為什麼值得另寫
- 尚待釐清的關鍵問題
- 既有素材或可作起點的來源連結

沒有值得保留的支線就省略。一般背景知識不必都轉成待辦。

## 12. 交付前檢查
